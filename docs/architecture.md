# Architecture

How the pieces fit together. Orientation, not an inventory — the file tree is the inventory, and it moves faster than prose. Written to survive renames: this describes relationships, and points to the docs that own each subsystem in detail.

React 19 + Next.js 16 (App Router). Colors are generated by [colorizr](https://github.com/gilbarbara/colorizr)'s `scale()`; everything else here exists to feed it options and render what comes back.

## What you build

A **palette**: an ordered list of up to ten **colors**, plus one set of **options** they share. Each color generates a **scale** — a ramp of 3–20 steps. That is the product. Everything else in the app is a verb on it or a lens over it.

The whole model is three fields (`GeneratorState`):

```ts
Palette    = { name?, colors: ColorEntry[], globalOptions: GlobalScaleOptions }
ColorEntry = { id, name, value: OklchString, group?, overrides? }
```

**Options exist at two levels, and that is the product.** The globals apply to every color; a color's `overrides` shadow them. `getEffectiveOptions` merges the two — globals first, then the color's overrides on top, with `saturation` dropped unless `saturationOverride` is on, so each color otherwise keeps its own natural chroma. Saturation is the one option that exists *only* at the global level (`ColorOverrides` omits it): a per-color copy would have to be de-duplicated against a global that is dead state whenever the override is off.

That one rule is why so much else looks the way it does. The URL carries two shapes of the same option (`?f=1.2` for the global, `f:1.2` on a color's own path segment). `setColorOverride` strips any override structurally equal to its global, so the URL never carries state that says nothing. `ScaleColorOptions` — the curve editor — is prop-driven and store-free, because it edits *an* options object rather than *the* options object; that is how one component serves both levels. And the Color Info table can label every row `default`, `custom`, or `override`.

**The globals are one bag, split across two surfaces.** `PALETTE_OPTION_KEYS` — steps, mode, variant, lock, saturation — are the Options panel in the palette header. `CURVE_OPTION_KEYS` — lightness range, lightness curve, chroma curve, hue shift — are Advanced Options in the sidebar, and are what the design-system presets write. Each surface has its own Reset, scoped to its own family. That split is why applying a preset does not clobber your step count.

**The first color is privileged.** `colors[0]` is the seed: `getDefaultGlobalOptions(seed)` derives the palette's defaults from it — notably `saturation`, which is the seed's own chroma as a percentage. Editing, removing, or reordering the first color therefore re-bases those defaults. Nothing writes them into the store, though: the defaults are *derived* on read, so the two levels stay clean in both directions. A stored `globalOptions.saturation` is only live while `saturationOverride` is on — see `docs/palette.md`.

**What you can do to a palette:**

- **Build it** — add a color (its hue is the last color's, rotated by the current spacing angle), remove, rename, reorder, randomize, pick.
- **Shape it** — the two option surfaces above, at either level, plus one-click Tailwind / Material / Bootstrap / Open Color presets.
- **Organize it** — give each color a group (brand, neutral, semantic, decorative), and filter the view by group.
- **Inspect it** — distribution charts, per-step Color Info (OKLCH, APCA contrast, gamut drift), and a contrast grid of every step against every other.
- **Preview it** — real components and typography rendered in your colors.
- **Take it** — export (five targets: Tailwind 4/3, CSS, SCSS, SVG — each offering the color notations that make sense for it, so SVG is hex-only and CSS/SCSS add RGB channels), share (the URL), save (needs an account).

Only the last is gated on auth. Naming, sharing and exporting are deliberately free.

**Everything downstream of `scale()` is a read-only projection.** The palette view, both export drawers, the preview's CSS custom properties, the charts, the info modal, the contrast grid — each reads the palette and computes. None of them write back.

## The URL is the state

The palette lives in the URL. The store follows it; there is no competing persisted copy, no autosave, no draft.

Nearly every design decision downstream falls out of this. Back/forward is undo/redo for free. Sharing is copying the address bar. A reload of an unsaved palette loses nothing. Saving is *not* how you keep a palette — it's how you give it a name and a home.

The cost is that the URL is a hot path: it is written on every structural edit, so writes must be cheap, ordered, and never fight the router.

**`docs/palette.md` is the authority** for the URL grammar, store seeding, the sync-hook lifecycle, and the history/router split. Read it before touching palette or navigation behavior.

## Render tree

`app/layout.tsx` renders `app/providers.tsx`, which composes the global tree: theme → HeroUI (with toasts) → auth → an app shell holding the header, the routed page inside a Sentry error boundary, and the login modal.

Two things about this tree are load-bearing:

**The generator route group is walled off.** `app/(generator)/layout.tsx` wraps `/` and `/p/*` — and nothing else — in `GeneratorStoreProvider`. That provider reads `useSearchParams`, which forces client rendering on everything beneath it. Everything outside that subtree (`/palettes`, `/about`, `/privacy`, `/terms`, and the content pages) must stay outside it or lose static rendering.

**The error boundary is keyed to a stable route key**, with every `/p*` path collapsing to one key. Otherwise each palette edit would remount the boundary.

## State: four scopes

There are four Zustand stores, but the number that matters is four **scopes**. Scope decides lifetime, and lifetime decides where a thing lives. When you add state, the question is not "which store" — it is "what is this scoped to".

| Scoped to | What | Lives in |
|---|---|---|
| the palette | `colors`, `globalOptions`, `name` | **the URL** |
| *this* palette, this session | `activeColorId`, `previewColorId`, `chartColorIds`, `groupFilter` | memory only |
| the user | `view`, `gamut`, `colorSpacing`, export formats, panel visibility | `localStorage` |
| the account | the saved palettes | Firestore |

The second row is the one that gets mishandled. That state is *palette-relative*: an active color, a previewed color, an open chart, a group filter — each means something only against the palette in front of you. Persist any of it and you carry a stale selection into the next palette. `appStore`'s own comment on `groupFilter` makes the argument, and it generalizes to the whole row.

The third row is the opposite: preferences about how you like to work, true across any palette, so they persist. `appStore` writes them through `partialize`, and a pre-paint script in `app/layout.tsx` re-applies them to `<html>` (`data-gamut`, `data-sidebar`, `data-preview`, and the two panel flags) before React mounts — so the first paint is already correct rather than flashing a default.

Mechanically: `appStore`, `authStore` and `palettesStore` are ordinary module singletons. **`generatorStore` is not.** It is a **per-request factory** (`createGeneratorStore`), handed down through Context and read via `useGenerator()` / `useGeneratorStoreApi()`. It has to be: the generator routes are `force-dynamic`, and a module-level store would be shared across requests on the server, leaking one visitor's palette into another's SSR output.

The provider seeds it once — from the parsed URL on `/p/*`, otherwise from a fallback palette that the layout generates **on the server** and passes down as a prop. Generating that random palette (random color + uuid) independently on the server and the client is what previously caused hydration mismatches.

## The scale pipeline

The effective options for a color (see *What you build*) are handed to `scale()`. Bounds and defaults for every option live in `src/config/scale.ts`.

**`scale()` has three independent consumers**, each computing from the palette rather than sharing a result: `Palette/Scale` (what you see), `ExportPalette` (what you copy — `utils/export.ts` only formats the steps it is handed), and `utils/preview-tokens.ts` (the live preview's CSS custom properties, which generates light and dark ramps at a minimum step count so the `50…900` slots always exist).

**Curve values are polymorphic**: a scalar is Simple mode, `{ low, high }` is Split, and `chromaCurve` additionally accepts a movable peak. `src/utils/scale-options.ts` owns normalization and the mode helpers, and is shared by the URL codec, the store, and the curve editors — so all three agree on what "unchanged" means.

Everything parsed out of a URL is range-checked and cross-validated before it can reach `scale()`, because colorizr throws on invalid input. Invalid values are dropped silently rather than surfaced.

## Color input mode vs. gamut

Two independent axes that are easy to conflate:

- **Input mode** (OKLCH / HSL / RGB) is per-color and cosmetic — it drives the text field and the channel sliders in the sidebar.
- **Gamut** (P3 / sRGB) is global and changes what swatches *paint* and what clicking one *copies*. It is implemented purely in CSS: every color surface emits both an OKLCH and a hex custom property, and a Tailwind variant picks one. No JS branch, therefore no hydration mismatch.

Neither affects export output, which has its own format setting.

**`docs/color-mode.md` is the authority** here.

## Auth and persistence

Firebase Authentication (Google, GitHub, email/password, magic link) behind `AuthProvider`, with `onAuthStateChanged` restoring the session. The SDK is dynamically imported on idle so it stays off the first-load path; if that import fails, the app settles as signed-out rather than breaking. A Cloud Function (`cloud-functions/`) runs `beforeUserCreated` to mark OAuth users verified, working around Firebase's trusted-provider overwrite.

`beforeUserCreated` is a v2 **blocking function**, which requires the Firebase project to be upgraded to **Identity Platform** (GCIP). It cannot be deployed on the free Auth tier. Nothing in the code says so — it is a property of the project, not the tree.

Saved palettes live in Firestore (Lite). The shape worth knowing: **the stored `url` is the structural form only** — no `?id=`, no `?name=`. Identity lives in the record's fields and is re-attached when the palette is read back. That means renaming a saved palette is a field write, not a URL rewrite, and a stored URL stays valid if the identity scheme changes.

Naming and sharing are deliberately **not** gated on auth. Only persistence is.

## Analytics

PostHog with autocapture **off** — every event is a manual `trackEvent(name, data)` call. Adding a control means adding its event; nothing is captured for you.

**`docs/events.md` is the authority** for naming and domains. Read it before adding, renaming, or moving an event. (`.agent/event-migration.md` is a historical record, not the spec.)

## Build and deploy

Next.js standalone output, Dockerized, on Dokploy. The one thing that bites: `NEXT_PUBLIC_*` variables are inlined into the client bundle at **build** time, so they must be present as build args — supplying them only at runtime produces a bundle with no Firebase config and no analytics.

`/p/*` and `/og/*` are server-rendered and require the Node server; they cannot be exported statically.
